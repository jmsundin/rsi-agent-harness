# Memory architectures and taxonomies for LLM agent harnesses (2025–2026)

Scope note: this file covers how agent memory is categorized and built (write / read / maintenance paths), the main frameworks and papers, benchmark evidence, failure modes, and how file-based plain-text memory compares with vector/graph stores. Older foundational work (2023–2024) is marked as such. Items flagged **[Ratchet]** are the ones most relevant to a version-controlled, text-playbook memory evaluated under a held-out gate.

## Key Question 1: What is the current consensus taxonomy for agent memory, and which distinctions matter in practice?

### Takeaway
There is no single consensus taxonomy, but 2025–26 surveys converge on two orthogonal axes that matter in practice: (a) *where memory lives* (parametric weights vs. non-parametric/"contextual" tokens or latents, and within tokens: in-context vs. external store), and (b) *what it is for* (facts about the world/user vs. experience/strategy/skills vs. transient working state). The older cognitive-science split (working / episodic / semantic / procedural, from CoALA) is still the lingua franca of frameworks like LangMem, but newer surveys argue it blurs in practice and instead foreground the *operations* (write, consolidate, index, retrieve, update, forget) as the design surface that actually differentiates systems.

### Cited Findings

**Foundational (2023) taxonomy still used by frameworks**
- CoALA (Sept 2023, foundational) organizes a language agent as working memory plus long-term memories, with a structured action space; it defines *retrieval* as reading from long-term memory, *reasoning* as updating working memory with the LLM, and *learning* as writing to long-term memory. Working memory "serves as the central hub connecting different components of a language agent." — [CoALA, arXiv 2309.02427](https://arxiv.org/abs/2309.02427); [CoALA OpenReview PDF](https://openreview.net/notes/edits/attachment?id=5OyZZmHdwV&name=pdf)
- LangMem's conceptual guide operationalizes the cognitive split for engineers: Semantic (facts; stored as a *profile* or a *collection*), Episodic (past experiences / few-shot examples / conversation summaries; collection), Procedural (system behavior; "prompt rules or collection"). — [LangMem Core Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)

**2025–26 surveys proposing new taxonomies**
- "Rethinking Memory in LLM based Agents" (May 2025, v3 Dec 2025) categorizes memory into *parametric* (implicit in weights) and *contextual* (explicit external data, structured or unstructured) and defines six core operations: Consolidation, Updating, Indexing, Forgetting, Retrieval, and Condensation; it maps these onto four research topics: long-term, long-context, parametric modification, and multi-source memory. — [arXiv 2505.00675](https://arxiv.org/abs/2505.00675)
- The same survey notes that in LLMs "the boundary between semantic and episodic memory is often blurred, as parametric representations may intertwine factual knowledge with contextual associations." — [arXiv 2505.00675 PDF](https://arxiv.org/pdf/2505.00675)
- "Memory in the Age of AI Agents" (Dec 2025, v2 Jan 2026) argues "the proliferation of diverse terminologies (declarative, episodic, semantic, parametric memory, etc.) further obscures conceptual clarity" and that short-term/long-term distinctions "have proven insufficient." It proposes three lenses: **forms** (token-level, parametric, latent), **functions** (factual, experiential, working), and **dynamics** (formation, evolution, retrieval). — [arXiv 2512.13564](https://arxiv.org/abs/2512.13564); [HTML v2](https://arxiv.org/html/2512.13564v2)
- That survey further splits *experiential memory* by abstraction level: "Case-based Memory preserves raw records for direct replay, Strategy-based Memory distills abstract heuristics for planning, and Skill-based Memory compiles executable capabilities for action," and classifies token-level memory as flat (1D), graph/structured (2D), or hierarchical (3D). — [arXiv 2512.13564 HTML](https://arxiv.org/html/2512.13564v2)
- "Memory for Autonomous LLM Agents: Mechanisms, Evaluation, and Emerging Frontiers" (Mar 2026) formalizes agent memory "as a write–manage–read loop tightly coupled with perception and action" and introduces a three-dimensional taxonomy "spanning temporal scope, representational substrate, and control policy," with five mechanism families: context-resident compression, retrieval-augmented stores, reflective self-improvement, hierarchical virtual context, and policy-learned management. It states "the parametric–non-parametric gap is real" with "different failure profiles." — [arXiv 2603.07670](https://arxiv.org/abs/2603.07670)
- A TMLR 2026 survey ("Rethinking Memory Mechanisms of Foundation Agents in the Second Half"), reviewing 500+ papers, uses three dimensions: memory substrate (internal vs. external), cognitive mechanism (episodic, semantic, sensory, working, procedural), and memory subject (user-centric vs. agent-centric). — [OpenReview review summary (UCSD mirror)](https://cseweb.ucsd.edu/~jmcauley/reviews/tmlr26.pdf)
- "Anatomy of Agentic Memory" (Feb 2026) classifies memory-augmented generation (MAG) systems "based on four memory structures" and criticizes prior surveys for ignoring benchmark saturation, metric validity, backbone sensitivity, and system cost. — [arXiv 2602.19320](https://arxiv.org/html/2602.19320v1)
- The security literature adds a lifecycle taxonomy: six phases WRITE, STORE, RETRIEVE, EXECUTE, SHARE & PROPAGATE, FORGET & ROLLBACK, crossed with four objectives (Integrity, Confidentiality, Availability, Governance). — [EMNLP 2026 LTM security survey](https://aclanthology.org/2026.emnlp-main.2296.pdf)

**Pipeline-stage taxonomy (the practical one)**
- LongMemEval decomposes long-term memory design into three stages—indexing, retrieval, reading—and four control points: value (what unit is stored), key (what it is indexed by), query (how the question is rewritten), and reading strategy. — [LongMemEval, arXiv 2410.10813](https://arxiv.org/html/2410.10813)
- LangMem distinguishes *active* ("hot path", during the conversation, immediate but adds latency) from *background* ("subconscious", after the conversation, no latency impact, deeper pattern analysis) memory formation. — [LangMem Core Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Letta's product taxonomy: *memory blocks* (core memory; "structured sections of the agent's context window that persist across all interactions ... always visible - no retrieval needed", each with `label`, `description`, `value`), *archival memory* ("semantically searchable database ... Agent-immutable ... Unlimited storage ... Tagged organization"), and recall/conversation memory. Guidance: "Information that should always be visible → Use memory blocks; Frequently changing state → Use memory blocks; Current working memory → Use scratchpad blocks." — [Letta memory blocks docs](https://docs.letta.com/guides/core-concepts/memory/memory-blocks); [Letta archival memory docs](https://docs.letta.com/guides/core-concepts/memory/archival-memory)
- Claude Code's taxonomy is *who writes it*: CLAUDE.md ("Instructions and rules", written by you) vs. auto memory ("Learnings and patterns", written by Claude), both loaded every session. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- A recent empirical paper (Oct 2026) argues memory type matters operationally: "existing retrieval-based memory approaches typically overlook the differences between memories and employ a unified strategy to process all memories, leading to suboptimal performance," proposing a memory-type-annotated dataset (TriMEM). — [arXiv 2610.11573](https://arxiv.org/abs/2610.11573)

### Inferences
- The distinctions that change engineering decisions are: (1) always-in-context vs. retrieved-on-demand (Letta blocks vs. archival; Claude Code MEMORY.md index vs. topic files; MemFS `system/` vs. rest of tree); (2) raw/non-lossy record vs. derived/abstracted knowledge (Zep episodes vs. entities; "case-based" vs. "strategy-based" experiential memory); (3) who/what is allowed to write (human-authored instructions vs. agent-written learnings vs. background consolidator); (4) hot-path vs. background write timing. The episodic/semantic/procedural labels are mostly a way to name *content types* within these.
- **[Ratchet]** A playbook edited by an outer self-improvement loop is "strategy-based experiential memory" in the 2512.13564 taxonomy and "procedural memory" in LangMem/CoALA terms; the outer loop is a background (sleep-time-style) consolidator; the held-out gate is a write-authorization policy. These mappings let you borrow evaluation and failure-mode literature from each line of work.

### Gaps
- No survey I found reports an empirical head-to-head showing that *labeling* memories by type (episodic vs. semantic etc.) improves downstream performance in general; TriMEM (Oct 2026) is the first attempt I found and I did not retrieve its results.
- The 2603.07670 survey's "control policy" dimension (hand-written heuristics vs. learned policies) is asserted but I did not retrieve comparative evidence between the two.

## Key Question 2: Which concrete architectures exist, how do they differ, and what empirical evidence backs them?

### Takeaway
Architectures fall into (i) OS-style virtual context with agent-edited in-context blocks (MemGPT/Letta), (ii) extract-then-store fact/note stores with LLM-driven update rules (Mem0, LangMem, A-MEM), (iii) temporal knowledge graphs (Zep/Graphiti, Mem0g, HippoRAG), (iv) scored episodic streams with periodic reflection (Generative Agents, MemoryBank), (v) experiential/procedural stores of reflections, workflows, skills or playbooks (Reflexion, Voyager, AWM, ReasoningBank, Memp, ACE), and (vi) plain files/markdown (Claude Code CLAUDE.md/auto memory, Anthropic memory tool, Letta MemFS). Benchmark evidence is real but contested: vendor numbers on LoCoMo disagree by 20+ points depending on harness, full-context baselines often beat memory systems on small benchmarks, and the one benchmark covering learning and forgetting (MemoryAgentBench) shows all retrieval-style memory systems failing at test-time learning and selective forgetting.

### Cited Findings

#### A. OS-style / self-editing in-context memory: MemGPT → Letta
- MemGPT (2023, foundational) "demonstrated the idea of self-editing memory in a simple chat use-case with two in-context memory blocks"; Letta persists each block "individually ... in the DB, with a unique `block_id`," and blocks can be shared across agents and edited by tools. — [Letta: Memory Blocks blog](https://www.letta.com/blog/memory-blocks)
- **Write/maintenance path – sleep-time compute (Apr 2025):** "the primary agent is not provided with tools to edit its core memory"; those tools are attached to a *sleep-time agent* that "has the ability to manage both the in-context memory of the primary agent as well as its own," transforming "raw context" into "learned context." — [Letta: Sleep-time Compute blog](https://www.letta.com/blog/sleep-time-compute)
- The sleep-time compute paper reports it "can reduce the amount of test-time compute needed to achieve the same accuracy by ~5x on Stateful GSM-Symbolic and Stateful AIME," increase accuracy "by up to 13% ... and 18%," and amortizing across related queries cuts average cost per query 2.5x; efficacy correlates with predictability of the user query. — [arXiv 2504.13171](https://arxiv.org/abs/2504.13171)
- **Representation (2026):** Letta agents now store memory in MemFS, "a git-backed memory filesystem" where "Files at the memory root are loaded into the agent's system prompt on every turn" and "The root `MEMORY.md` lists them, so directory and file names act as signposts the agent follows to read the right file." Each file is Markdown with YAML frontmatter (`description`). — [Letta MemFS docs](https://docs.letta.com/concepts/memfs/index.md); [Letta Agent MemFS](https://docs.letta.com/letta-agent/concepts/memfs)
- Letta Code "Context Repositories" (Feb 2026) are "git-backed, so every change to memory is automatically versioned with informative commit messages"; a background "memory reflection" skill "periodically reviews recent conversation history and persists important information ... works in a git worktree," and a "memory defragmentation" skill "backs up the agent's memory filesystem, then launches a subagent that reorganizes files, splitting large files, merging duplicates, and restructuring into a clean hierarchy of 15–25 focused files." — [Letta: Context Repositories blog](https://www.letta.com/blog/context-repositories)
- "Dreaming" can be triggered "after a set number of completed agent steps or when the context window is compacted"; users can teach explicitly with `/remember`. — [Letta Memory & dreaming docs](https://docs.letta.com/configuration/memory)
- **Results:** MemGPT scored 93.4% on the Deep Memory Retrieval (DMR) benchmark with gpt-4-turbo (as reported in Zep's paper); a full-conversation baseline scored 94.4% and 98.0% with gpt-4o-mini. — [Zep paper, arXiv 2501.13956](https://arxiv.org/html/2501.13956)
- Letta's own filesystem experiment: "Letta agents running on gpt-4o-mini achieve 74.0% accuracy on LoCoMo by simply storing conversation histories in files, rather than using specialized memory or retrieval tools," above "Mem0's reported 68.5% score for their top-performing graph variant." The agent was constrained by tool rules to call `search_files` repeatedly before `answer_question`. — [Letta: Benchmarking AI Agent Memory](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- Letta's June 2026 research direction: "memory models ... trained to generate memories during sleep-time (aka 'agent dreaming') which improve future task performance," optimized "end-to-end through meta-RL." — [Letta: Memory Models blog](https://www.letta.com/blog/towards-agents-that-learn/)

#### B. Scored episodic stream + reflection: Generative Agents (2023, foundational)
- Memory stream retrieval "combines relevance, recency, and importance"; scores are min-max normalized to [0,1] and summed. Reflections are generated "when the sum of the importance scores for the latest events perceived by the agents exceeds a threshold (150 in our implementation)," using "the 100 most recent records in the agent's memory stream" to pose questions; reflections are stored back "including pointers to the memory objects that were cited." — [Generative Agents, ACM DL](https://dl.acm.org/doi/fullHtml/10.1145/3586183.3606763); [arXiv 2304.03442](https://arxiv.org/pdf/2304.03442)
- The 2026 survey calls this "multi-signal scoring ... a substantial improvement over pure cosine similarity" that "remains influential in later designs." — [arXiv 2603.07670](http://arxiv.org/html/2603.07670v1)

#### C. Forgetting-curve stores: MemoryBank (2023, foundational)
- MemoryBank's update mechanism is "inspired by the Ebbinghaus Forgetting Curve," letting the model "forget and reinforce memory based on time elapsed and the relative significance of the memory." — [MemoryBank, AAAI 2024](https://doi.org/10.1609/aaai.v38i17.29946); [arXiv 2305.10250](https://arxiv.org/abs/2305.10250)
- In later evaluations MemoryBank is the weakest baseline: on LoCoMo (Mem0 paper's table) MemoryBank F1 = 5.00 single-hop, 5.56 multi-hop, 6.61 open-domain, 9.68 temporal. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- An ACT-R-inspired variant (Jan 2026) implements activation-based decay where "relevant memories are selectively reinforced through use, while irrelevant ones fade over time." — [ACM HAI 2026](https://dl.acm.org/doi/full/10.1145/3765766.3765803)

#### D. Verbal reflection and skill libraries (2023, foundational): Reflexion, Voyager
- Reflexion agents "verbally reflect on task feedback signals, then maintain their own reflective text in an episodic memory buffer"; 91% pass@1 on HumanEval. — [Reflexion, arXiv 2303.11366](https://arxiv.org/abs/2303.11366) (the 2026 survey gives the GPT-4 baseline as 80% — [arXiv 2603.07670](http://arxiv.org/html/2603.07670v1))
- Voyager stores "an ever-growing skill library of executable code for storing and retrieving complex behaviors"; skills are "temporally extended, interpretable, and compositional, which compounds the agent's abilities rapidly and alleviates catastrophic forgetting"; 3.3x more unique items, 2.3x longer distances, tech-tree milestones up to 15.3x faster; "Voyager w/o skill library exhibits a tendency to plateau in the later stages." — [Voyager, arXiv 2305.16291](https://arxiv.org/abs/2305.16291); [HTML](https://arxiv.org/html/2305.16291v1)

#### E. Graph-structured retrieval: HippoRAG (2024) / HippoRAG 2 (2025)
- HippoRAG "orchestrates LLMs, knowledge graphs, and the Personalized PageRank algorithm," beating SOTA multi-hop QA "by up to 20%"; single-step retrieval matches iterative IRCoT "while being 10-30 times cheaper and 6-13 times faster." — [arXiv 2405.14831](https://arxiv.org/abs/2405.14831)
- HippoRAG 2 (Feb 2025) notes that structure-augmented RAG variants' "performance on more basic factual memory tasks drops considerably below standard RAG"; HippoRAG 2 fixes this via "deeper passage integration" and reports "a 7% improvement in associative memory tasks over the state-of-the-art embedding model." — [arXiv 2502.14802](https://arxiv.org/abs/2502.14802)

#### F. Agentic note networks: A-MEM (Feb 2025)
- Each note holds original content, timestamp, LLM-generated keywords, tags, a contextual description, and a set of links. Adding a memory triggers *link generation* (retrieve nearest neighbors, LLM decides links) and *memory evolution* ("the system determines whether to update its context, keywords, and tags" of neighbors; "The evolved memory m_j* then replaces the original memory m_j"). — [A-MEM, arXiv 2502.12110](https://arxiv.org/html/2502.12110)
- Results on LoCoMo (F1/BLEU-1): with GPT-4o-mini A-Mem uses 1,137 tokens vs 16,910 for the full-context LoCoMo baseline, with higher temporal F1 (27.59 vs 18.41) but lower single-hop (17.23 vs 40.36) and multi-hop (12.57 vs 25.02). Removing link generation and evolution causes "substantial performance degradation, particularly in Multi Hop reasoning and Open Domain tasks." — [A-MEM HTML](https://arxiv.org/html/2502.12110)
- Caveat: when Mem0 re-ran A-Mem with an LLM-judge metric ("A-Mem*"), it scored J = 39.79 single-hop and 18.85 multi-hop, "more than 25 points" below Mem0. — [Mem0 paper](https://arxiv.org/html/2504.19413)

#### G. Extract-then-update fact stores: Mem0 and Mem0g (Apr 2025; new algorithm Apr 2026)
- **Write path:** an extraction phase "processes messages and historical context to create new memories"; an update phase "evaluates each candidate fact against existing memories ... For each fact, the system first retrieves the top s semantically similar memories" and applies a memory operation "through a Tool Call mechanism." Mem0g adds "entity extraction and ... relation triplets" with "conflict detection and resolution." — [Mem0 paper, arXiv 2504.19413](https://arxiv.org/html/2504.19413)
- Current Mem0 docs describe `add` as "Additive storage: New memories are added without overwriting or deleting existing memories" and the capability table lists "Add behavior: ADD-only; memories accumulate" for both Platform and OSS; they also offer `expiration_date` (expired memories hidden from `search`) and warn that `infer=False` raw inserts can create duplicates. — [Mem0 docs: Add Memory](https://docs.mem0.ai/core-concepts/memory-operations) (this appears to differ from the paper's described update phase; treat the current write semantics as uncertain)
- **Results (paper):** Mem0 claims "26% relative improvements in the LLM-as-a-Judge metric over OpenAI," Mem0g "around 2% higher overall score than the base configuration," "91% lower p95 latency and ... more than 90% token cost" savings vs full-context. Per-category J: Mem0 single-hop 67.13, multi-hop 51.15, open-domain 72.93, temporal 55.51; Mem0g 65.71 / 47.19 / 75.71 / 58.13; Zep 61.70 / 41.35 / 76.60 / 49.31; LangMem 62.23 / 47.92 / 71.12 / 23.43; OpenAI 63.79 / 42.92 / 62.29 / 21.71. Mem0g's overall J of 68.44 trails "only the computationally prohibitive full-context approach." Zep's graph "consumes in excess of 600k tokens" for memory construction. — [arXiv 2504.19413](https://arxiv.org/abs/2504.19413); [HTML](https://arxiv.org/html/2504.19413)
- Independent reading of the same table: the graph variant "lost single-hop and multi-hop, ran search about 3x slower, and cost about 2x the tokens," edging ahead overall 68.44 to 66.88. — [Codepointer analysis](https://codepointer.substack.com/p/agent-memory-systems-and-knowledge)
- **April 2026 "new memory algorithm"** (managed platform, "proprietary optimizations not available in the open-source"): LoCoMo 71.4 → 92.5, LongMemEval 67.8 → 94.4, BEAM (1M) 64.1, BEAM (10M) 48.6, ~7K tokens retrieved, ~1s p50, "single-pass retrieval (one call, no agentic loops) at a top_200 retrieval budget." — [mem0ai/mem0 README](https://github.com/mem0ai/mem0)

#### H. Temporal knowledge graph: Zep / Graphiti (Jan 2025)
- Graph has three tiers: an **episode subgraph** (raw messages/text/JSON, "a non-lossy data store"), a **semantic entity subgraph** (entities resolved against existing nodes via 1024-d embedding cosine search plus full-text search and an LLM resolution prompt, using the last n=4 messages as context), and a **community subgraph** (map-reduce summaries). — [Zep paper, arXiv 2501.13956](https://arxiv.org/html/2501.13956)
- **Maintenance path – bi-temporal invalidation:** edges carry t'_created / t'_expired (ingestion timeline) and t_valid / t_invalid (event timeline); "The system employs an LLM to compare new edges against semantically related existing edges to identify potential contradictions. When the system identifies temporally overlapping contradictions, it invalidates the affected edges by setting their t_invalid to the t_valid of the invalidating edge," prioritizing new information. — [Zep paper](https://arxiv.org/html/2501.13956)
- **Read path:** cosine similarity, Okapi BM25, and breadth-first graph search for recall; rerankers RRF, MMR, an "episode-mentions reranker" (frequency of mentions), and a "node distance reranker." — [Zep paper](https://arxiv.org/html/2501.13956)
- **Results:** DMR 94.8% vs MemGPT 93.4% (gpt-4-turbo); LongMemEval with gpt-4o: Zep 71.2% vs full-context 60.2%, latency 2.58s vs 28.9s, 1.6k vs 115k context tokens. — [Zep paper](https://arxiv.org/html/2501.13956). Zep's current research page claims LoCoMo 94.7% (155 ms retrieval, 5,760 tokens) and LongMemEval 90.2% (451/500). — [Zep Research](https://www.getzep.com/research)
- The 2512.13564 survey classes Zep as "Entity-Level ... Temporal KG ... 3-layer graph (Episodic, Semantic, Community)" and Mem0/MemGPT as "Incremental ... Textual Summary." — [arXiv 2512.13564](https://arxiv.org/html/2512.13564v2)

#### I. The Mem0–Zep LoCoMo dispute (a cautionary tale for benchmarking)
- Zep accused Mem0's paper of using "a flawed implementation" of Zep and noted "Mem0's own results show their system being outperformed by a simple full-context baseline"; after Mem0's CTO filed an issue, Zep corrected its own LoCoMo claim from 84% to "75.14% +/- 0.17 (over 10 runs)" by restricting to the first four validated categories and aligning the system prompt, and urged evaluation on LongMemEval "which avoids the critical flaws we identified in LoCoMo." — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory); [getzep/zep-papers issue #5](https://github.com/getzep/zep-papers/issues/5)
- Mem0's 2026 comparison page: "LongMemEval overall accuracy: Mem0 93.4 vs Zep 71.2 (GPT-4o)"; "LoCoMo has an active methodology dispute between the two teams"; Mem0 concedes it does not publish a matched full-context baseline for its 93.4. — [Mem0: Zep vs Mem0](https://mem0.ai/blog/zep-vs-mem0-which-ai-memory-layer-should-you-choose)
- Mem0's benchmark guide lists LoCoMo scores "Mem0 92.5% · Zep 94.7% (claimed) · ByteRover 92.2% · Dakera 88.2% · ZeroMemory 96.1% (claimed)" and flags that these are "Self-reported; not independently verified." — [Mem0 benchmark guide](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)
- Letta separately reported it "was unable to determine a way to backfill LoCoMo data into MemGPT/Letta without significant refactoring" and that Mem0 "did not respond" to clarification requests about its MemGPT numbers. — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory)

#### J. LangMem / LangGraph (Feb 2025)
- Provides "memory tools that agents can use to record and search information during active conversations 'in the hot path'" and a "Background memory manager that automatically extracts, consolidates, and updates agent memories." Memories live in a LangGraph `BaseStore` (InMemoryStore or AsyncPostgresStore) under hierarchical namespaces such as `("acme_corp", "{user_id}", "code_assistant")`, retrievable by key, semantic search, or metadata filter. — [langchain-ai/langmem](https://github.com/langchain-ai/langmem); [LangMem Core Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Each memory operation follows one pattern: "Accept conversation(s) and current memory state; Prompt an LLM to determine how to expand or consolidate the memory state; Respond with the updated memory state." Collections require reconciling new info "either deleting/invalidating or updating/consolidating existing memories"; "If the system over-extracts, this could lead to reduced precision ... If it under-extracts, ... low recall." Procedural memory "starts with system prompts ... then evolves through feedback" (prompt optimizers). — [LangMem Core Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- The launch post: "Some memories (core procedural memory) may be data-independent - they are always present in the prompt. Some are data-dependent and may be recalled based on semantic similarity." — [LangMem SDK launch](https://www.langchain.com/blog/langmem-sdk-launch)

#### K. OpenAI ChatGPT memory
- Two mechanisms: "Saved memories are details that you explicitly ask ChatGPT to remember or that ChatGPT saves as useful context," stored separately from chat history; "Reference chat history" lets it draw on past chats with "no separate storage limit." "Improved Memory continually updates a broader summary of relevant context. Legacy saved memories use a more explicit list of individual memory items." — [OpenAI Help: Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)
- Evidence: on LongMemEval, ChatGPT (GPT-4o) scored 0.5773 vs 0.9184 for offline reading with the same model (a 37% drop); Coze dropped 64%. — [LongMemEval](https://arxiv.org/html/2410.10813). In Mem0's LoCoMo run, OpenAI memory scored J = 21.71 on temporal questions "primarily due to missing timestamps in most generated memories despite explicit prompting." — [Mem0 paper](https://arxiv.org/html/2504.19413)

#### L. Anthropic: memory tool, context editing, Claude Code
- The Claude Developer Platform **memory tool** is "a file-based system. Claude can create, read, update, and delete files in a dedicated memory directory stored in your infrastructure"; it "operates entirely client-side through tool calls." **Context editing** "automatically clears stale tool calls and results from within the context window when approaching token limits." On an internal agentic-search eval, "combining the memory tool with context editing improved performance by 39% over baseline. Context editing alone delivered a 29% improvement"; in a 100-turn web search eval context editing reduced token consumption by 84%. — [Anthropic: Managing context](https://www.anthropic.com/news/context-management)
- Anthropic's context-engineering guidance names "Structured note-taking, or agentic memory" ("the agent regularly writes notes persisted to memory outside of the context window ... pulled back into the context window at later times"), e.g., "maintaining a NOTES.md file," as a low-overhead persistent memory. — [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Claude Code auto memory** lives at `~/.claude/projects/<project>/memory/` with `MEMORY.md` as "an index of the memory directory," one line per memory, plus topic files. "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation." After a write, Claude Code checks the limits and "reminds Claude to shorten it: keep one line per entry, move detail into topic files, and merge or drop stale entries"; over-limit writes return an error telling Claude to rewrite the index. Writes with frontmatter get a `modified` ISO-8601 timestamp "so ... how current the fact is" is visible. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Four auto-memory note types recorded in frontmatter `type`: `user` (role, expertise, preferences), `feedback` ("corrections you give Claude and approaches you confirm"), `project` ("ongoing work, deadlines, and decisions that Claude can't derive from the code or git history"), `reference` (where to find external info). "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- CLAUDE.md guidance: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"; "if two instructions contradict each other, Claude may pick one arbitrarily"; files are concatenated root-down (closest read last); `@path` imports (depth 4) "don't reduce the context cost"; `.claude/rules/` with `paths:` frontmatter load on demand; whole files up to 4 MiB load, but on-demand files are truncated at 40,000 chars (200K context). Project-root CLAUDE.md "survives compaction: after `/compact`, Claude re-reads it from disk." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)

#### M. Experiential / procedural / playbook memory (most relevant to self-improving harnesses)
- **Agent Workflow Memory (2024):** induces reusable "workflows" from past trajectories (offline from training examples or online from test queries) and improves Mind2Web and WebArena "by 24.6% and 51.1% relative success rate" while reducing steps. — [AWM, arXiv 2409.07429](https://arxiv.org/abs/2409.07429)
- **ReasoningBank (Google, Sep 2025):** "distills generalizable reasoning strategies from an agent's self-judged successful and failed experiences"; "unlike existing workflow memory strategies that only focus on successful runs, ReasoningBank actively analyzes failed experiences." It "consistently outperforms existing memory mechanisms that store raw trajectories or only successful task routines" on web-browsing and SWE benchmarks, and memory-aware test-time scaling (MaTTS) amplifies gains. — [arXiv 2509.25140](https://arxiv.org/abs/2509.25140); [Google Research blog](https://research.google/blog/reasoningbank-enabling-agents-to-learn-from-experience)
- **Memp (ACL 2026):** "distills past agent trajectories into both fine-grained, step-by-step instructions and higher-level, script-like abstractions," with "a dynamic regimen that continuously updates, corrects, and deprecates its contents"; on TravelPlanner and ALFWorld success rises as the repository is refined, and "migrating the procedural memory to a weaker model can also yield" gains. — [Memp, arXiv 2508.06433](https://arxiv.org/abs/2508.06433); [ACL Anthology](https://aclanthology.org/2026.findings-acl.866/)
- **ACE – Agentic Context Engineering (ICLR 2026):** "treats contexts as evolving playbooks that accumulate, refine, and organize strategies through a modular process of generation, reflection, and curation." Three roles: Generator (trajectories), Reflector ("distills concrete insights from successes and errors"), Curator (merges "compact delta entries ... deterministically ... by lightweight, non-LLM logic"). Each *bullet* has "a unique identifier and counters tracking how often it was marked helpful or harmful" plus content ("a reusable strategy, domain concept, or common failure mode"). *Grow-and-refine*: new bullets appended, existing updated in place, then "A de-duplication step ... prunes redundancy by comparing bullets via semantic embeddings." — [ACE, arXiv 2510.04618](https://arxiv.org/html/2510.04618v2)
- ACE results: "+10.6% on agents and +8.6% on finance"; on AppWorld it "matches the top-ranked production-level agent IBM-CUGA (powered by GPT-4.1) on average and surpasses it on the harder test-challenge split" using DeepSeek-V3.1; offline ReAct+ACE beats ReAct+ICL and ReAct+GEPA by 12.3% and 11.9%; online it beats Dynamic Cheatsheet by 7.6%; "even without access to ground-truth labels ... an average improvement of 14.8% over the ReAct baseline" using execution feedback. Cost: 82.3% lower adaptation latency and 75.1% fewer rollouts than GEPA; 91.5% lower latency and 83.6% lower token cost than Dynamic Cheatsheet online. Limitation: "Tasks like HotPotQA often benefit more from concise, high-level instructions ... than from long contexts." — [ACE HTML](https://arxiv.org/html/2510.04618v2); [Microsoft Research page](https://www.microsoft.com/en-us/research/publication/agentic-context-engineering-evolving-contexts-for-self-improving-language-models/)

#### N. Benchmarks and what they show
- **LoCoMo (ACL 2024):** per Mem0, "10 extended conversations, each containing approximately 600 dialogues and 26000 tokens on average"; per a secondary source "about 300 turns and 9K tokens over up to 35 sessions" (sources disagree on token counts). — [Mem0 paper](https://arxiv.org/html/2504.19413); [aiagentmemory.org](https://aiagentmemory.org/articles/llm-memory-evaluation/). MemoryAgentBench says LoCoMo "still features relatively short conversations (~9k)." — [MemoryAgentBench PDF](https://proceedings.iclr.cc/paper_files/paper/2026/file/fd1eff9dd295df50a41f2521942fa31d-Paper-Conference.pdf)
- **LongMemEval (ICLR 2025):** 500 questions over five abilities (information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention); LongMemEval_S ≈115k tokens/question, LongMemEval_M ≈1.5M tokens. Long-context LLMs show "a 30% to 60% performance decline" reading the whole history vs oracle sessions. Design findings: expanding keys with extracted user facts (K = V + fact) gives "9.4% higher recall@k" and "5.4% higher accuracy"; time-aware query expansion improves temporal recall "by 6.8% ~ 11.3%" but "depends on using a strong LLM"; decomposing sessions into rounds helps; "even with perfect retrieval, a suboptimal reading strategy results in up to a 10-point absolute performance drop." — [LongMemEval](https://arxiv.org/html/2410.10813); [ICLR 2025 page](https://proceedings.iclr.cc/paper_files/paper/2025/hash/d813d324dbf0598bbdc9c8e79740ed01-Abstract-Conference.html)
- **MemBench (ACL Findings 2025):** separates "factual memory and reflective memory," "participation and observation" scenarios, and reports accuracy, recall, capacity, and temporal metrics. — [MemBench](https://aclanthology.org/2025.findings-acl.989); [arXiv 2506.21605](https://arxiv.org/abs/2506.21605)
- **MemoryAgentBench (ICLR 2026):** four competencies—accurate retrieval (AR), test-time learning (TTL), long-range understanding (LRU), selective forgetting (SF)—2,071 questions over 103k–1.44M-token inputs fed incrementally. Findings: "Long-context models achieve the best performance on TTL and LRU. This highlights a fundamental limitation of RAG methods and commercial memory agents, which still follow an agentic RAG paradigm"; on TTL classification with a GPT-4o-mini backbone (which alone scores 93/93/87 on BANKING/CLINC/NLU), Mem0 scored 35/37/35, Cognee 34/42/42, Zep 83/74/70, MemGPT 89/83/79, HippoRAG-v2 81/86/73. "Forgetting out-of-date memory poses a significant challenge on memory agents" (GPT-4o: 60.0 single-hop / 5.0 multi-hop on fact consolidation). Smaller chunks help AR but hurt LRU. MIRIX with GPT-4.1-mini cost $0.016 vs $0.043 for long-context GPT-4.1-mini on MH-Doc QA while scoring 75.0 vs 66.0. — [MemoryAgentBench, arXiv 2507.05257](https://arxiv.org/html/2507.05257); [ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/fd1eff9dd295df50a41f2521942fa31d-Abstract.html)
- **Memora (ACL Findings 2026):** benchmarks "memory consolidation and mutation" over weekly/monthly/quarterly horizons, noting prior benchmarks (LoCoMo, LongMemEval, PersonaMem) contain almost no memory mutations. — [Memora](https://aclanthology.org/2026.findings-acl.1337.pdf)
- **Benchmark validity critique (Anatomy of Agentic Memory, Feb 2026):** rates "Theoretical Saturation Risk" as High for HotpotQA and MemBench (~100k tokens "Fits in 128k Window"), Moderate for LoCoMo (~20k tokens, 35 sessions) and LongMemEval-S, Low for LongMemEval-M (>1M); proposes measuring a *Context Saturation Gap* Δ = MAG performance minus full-context baseline, with a benchmark valid only when Δ ≫ 0. Also flags "metric misalignment (e.g., F1 vs. semantic correctness), prompt sensitivity in LLM-as-a-judge evaluation." — [arXiv 2602.19320](https://arxiv.org/html/2602.19320v1)
- **System cost ("Agency Tax"):** per-turn retrieval latency ranges from 0.009 s (SimpleMem) and 0.062 s (A-Mem) to 31.2 s (MemoryOS); offline construction tokens from 1.3M (SimpleMem) to 7.04M (Nemori). — [arXiv 2602.19320](https://arxiv.org/html/2602.19320v1)
- Letta's view: LoCoMo-style results suggest "current memory benchmarks may not be very meaningful, and ... memory is more about how agents manage context than the exact retrieval mechanism used"; its Letta Leaderboard instead "creates memory interactions on-the-fly" with framework held constant. — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory)

### Inferences
- Across LoCoMo/LongMemEval, the biggest wins come from *indexing hygiene* (fact-augmented keys, timestamps on every memory, round-level granularity, time-scoped queries) rather than from exotic structure; graph variants buy small gains on temporal/relational questions at 2–3x cost and lose on simple retrieval.
- Vendor-reported scores on LoCoMo/LongMemEval (90%+) are not comparable across vendors or with the 2025 papers (60–70%) because harnesses, judges, model backbones, and category subsets differ; the only reliably comparable numbers are within a single paper's table.
- The MemoryAgentBench TTL/SF results are the most important negative evidence for Ratchet-like use: fact-extraction stores are poor at *learning procedures from history* and at *retiring outdated knowledge*, while agentic search over raw records (MemGPT-style, Letta filesystem) does much better at learning tasks.
- **[Ratchet]** ACE is the closest published analogue to an outer loop editing a text playbook; its measurable design choices (itemized bullets with ids and helpful/harmful counters, delta edits instead of rewrites, deterministic merge, embedding-based dedup, Reflector separated from Curator, offline warm-up then online adaptation) and its reported failure of label-free adaptation on concise-instruction tasks are directly testable in a held-out-gate loop.

### Gaps
- I could not retrieve Mem0's current open-source update semantics authoritatively; the paper describes an update phase with distinct operations while current docs say "ADD-only; memories accumulate." The exact operation names (e.g., ADD/UPDATE/DELETE/NOOP) were not visible in what I fetched.
- ReasoningBank's abstract does not give numbers; I did not retrieve the paper body for its percentage gains.
- The Mem0 2026 numbers (92.5 LoCoMo, 94.4 LongMemEval) and Zep's 94.7/90.2 are vendor self-reports; I found no independent replication.
- MemBench's reported system scores were not retrieved.
- No source found that directly benchmarks CLAUDE.md-style memory against vector stores on the *same* task.

## Key Question 3: What are the common failure modes (stale memories, retrieval noise, context bloat, memory poisoning, catastrophic overwrite)?

### Takeaway
The best-documented failure modes are: (1) stale/contradictory memories that no system reliably retires (MemoryAgentBench's selective-forgetting results are near-floor); (2) retrieval noise from over-extraction or mis-chunking and from retrieval-based memories failing to capture learning signal; (3) context bloat and "context rot," where longer histories or instruction files degrade adherence and accuracy while raising cost; (4) catastrophic overwrite via "context collapse" and "brevity bias" when an LLM rewrites a whole memory or prompt; (5) memory poisoning, which persists in ~84% of cases across harness/backends and can be seeded by query-only interaction; and (6) silent corruption when weaker backbones emit malformed structured writes.

### Cited Findings

**Stale, outdated, or conflicting memories**
- "Although being a well-discussed task in model-editing community ..., forgetting out-of-date memory poses a significant challenge on memory agents"; failures stem from "their inability to accurately identify and discard outdated information across extended interaction histories." — [MemoryAgentBench](https://arxiv.org/html/2507.05257)
- LongMemEval includes a dedicated "knowledge updates" ability; "Naive time-agnostic memory designs perform poorly on temporal reasoning questions." — [LongMemEval](https://arxiv.org/html/2410.10813)
- Mitigations in deployed systems: Zep's bi-temporal edge invalidation (new facts set `t_invalid` on contradicted edges). — [Zep paper](https://arxiv.org/html/2501.13956); Mem0's `expiration_date` field. — [Mem0 docs](https://docs.mem0.ai/core-concepts/memory-operations); Claude Code's `modified` timestamp and reminders to "merge or drop stale entries." — [Claude Code memory docs](https://code.claude.com/docs/en/memory); Memp's regimen that "updates, corrects, and deprecates" procedures. — [Memp](https://arxiv.org/abs/2508.06433)
- Claude Code warns that contradictory instructions across CLAUDE.md files mean "Claude may pick one arbitrarily," and recommends periodic review "to remove outdated or conflicting instructions." — [Claude Code memory docs](https://code.claude.com/docs/en/memory)

**Retrieval noise and over/under-extraction**
- "If the system over-extracts, this could lead to reduced precision of memories when your agent needs to search the store. If it under-extracts, this could lead to low recall." — [LangMem Core Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- "RAG-based agents generally underperform compared to their respective GPT-4o-mini backbones" on test-time learning; "RAG-based methods often struggle to more accurately retrieve context from memory that is closely associated with the input." Smaller chunks improve accurate retrieval but "for tasks requiring Long-Range Understanding (LRU), varying the chunk size hurts the performance." — [MemoryAgentBench](https://arxiv.org/html/2507.05257)
- Mem0 found the OpenAI memory baseline lost temporal reasoning because memories lacked timestamps even when prompted to include them. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Zep's paper notes rerankers are needed because initial search "aim[s] to achieve high recall," and its graph "consumes in excess of 600k tokens" due to "extensive redundancy." — [Zep paper](https://arxiv.org/html/2501.13956); [Mem0 paper](https://arxiv.org/html/2504.19413)
- A-MEM's "memory evolution" rewrites neighboring notes' context/keywords/tags and the evolved note "replaces the original memory." — [A-MEM](https://arxiv.org/html/2502.12110)

**Context bloat and "context rot"**
- Research agents' "performance often degrades as interaction histories grow. This degradation, known as context rot, reflects a failure to maintain coherent and task-relevant internal states"; "raw accumulation or passive summarization ... allowing early errors or misplaced emphasis to persist." ARC (reflection-driven context revision) "consistently outperforms passive context compression." — [ARC, ACL Findings 2026](https://aclanthology.org/2026.findings-acl.930)
- Long-context LLMs lose 30–60% accuracy reading a full ~115k-token history vs oracle sessions; commercial assistants drop 37–64%. — [LongMemEval](https://arxiv.org/html/2410.10813)
- "Files over 200 lines consume more context and may reduce adherence." Imports don't reduce context cost. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Context files for coding agents "increase the # steps in every setting ... leading to a significant (p-value < 0.001%) cost increase of 20% and 23%," and raise reasoning tokens by up to 22%, without improving success. — [Evaluating AGENTS.md, arXiv 2602.11988](https://arxiv.org/html/2602.11988)
- Anthropic: "once a tool has been called deep in the message history, why would the agent need to see the raw result again?"; context editing removes stale tool results and alone yields +29%. — [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [Anthropic news](https://www.anthropic.com/news/context-management)

**Catastrophic overwrite: context collapse and brevity bias**
- ACE documents **context collapse**: "when an LLM is tasked with fully rewriting the accumulated context at each adaptation step ... the model tends to compress it into much shorter, less informative summaries, causing a dramatic loss of information"; "a fundamental risk of end-to-end context rewriting with LLMs, where accumulated knowledge can be abruptly erased instead of preserved." — [ACE](https://arxiv.org/html/2510.04618v2)
- **Brevity bias**: "the tendency of optimization to collapse toward short, generic prompts"; GEPA "highlights brevity as a strength, but such abstraction can omit domain-specific heuristics, tool-use guidelines, or common failure modes." Prior work on prompt optimization for test generation found "iterative methods repeatedly produced near-identical instructions." — [ACE](https://arxiv.org/html/2510.04618v2)
- Fix: "incremental delta updates ... replace costly monolithic rewrites with localized edits" and "grow-and-refine ... balances steady context expansion with redundancy control." — [ACE](https://arxiv.org/html/2510.04618v2)

**Memory poisoning and injection**
- AgentPoison (NeurIPS 2024): backdoor via poisoned long-term memory/RAG store achieves "average attack success rate of ≥80% with minimal impact on benign performance (≤1%) with a poison rate <0.1%." — [AgentPoison](https://proceedings.neurips.cc/paper_files/paper/2024/hash/eb113910e9c3f6242541c1652e30dfd6-Abstract-Conference.html)
- MINJA (NeurIPS 2025): attacker "injects malicious records into the memory bank by only interacting with the agent via queries and output observations," using an "indication prompt" and "progressive shortening strategy" so records are retrieved for later victim queries. — [MINJA, arXiv 2503.03704](https://arxiv.org/abs/2503.03704); [NeurIPS page](https://proceedings.neurips.cc//paper_files/paper/2025/hash/42a97bbd9844d2bf68596730af80bcdf-Abstract-Conference.html)
- MemSecBench (Jul 2026): 310 cases, 24 configurations (2 harnesses × 4 memory backends × 3 LLMs). "malicious memory persists in 84.2% of all cases, and the full Write–Execute chain succeeds in 50.3%"; among poisoned cases "59.6% complete the full Execute chain, while 56.1% achieve selective repair"; backends differ by up to 16.1 points in attack success and 41.3 points in selective repair. — [MemSecBench, arXiv 2607.27080](https://arxiv.org/abs/2607.27080)
- LTM security survey (EMNLP 2026): three properties of LTM threats—Persistence ("recalled across an indefinite number of future sessions"), Statefulness ("a cluster of subtly biased episodic memories may exhibit behavioral drift long before any single memory entry triggers a conventional safety classifier"), and propagation. "A sufficiently salient retrieved memory can override explicit user instructions," making poisoning "a control-flow problem." STORE-time defenses "remain comparatively underdeveloped." It proposes Verifiable Memory Governance primitives: Write Authorization, Provenance Visibility, Principal-Scoped Retrieval, Rollbackability ("versioned snapshots and write logs sufficient to restore the memory store to a known-safe state"), Verified Forgetting. "robust LTM security cannot be retrofitted at retrieval or execution time alone, but must be anchored in storage-time provenance, versioning, and policy-aware retention." Example write-time defenses: VerificAgent's "human-verified freezing, where candidate memories are audited before being committed," MemCube metadata (source, version, sensitivity, time). — [EMNLP 2026 survey](https://aclanthology.org/2026.emnlp-main.2296.pdf)

**Silent corruption from weak backbones; benchmark/metric failures**
- "Silent Failure": with Qwen-2.5-3B, Nemori's format error rate during memory updates rose to 30.38% (vs 17.91% with gpt-4o-mini) and answer score fell from 0.781 to 0.447; "Append-only systems are relatively robust ... graph-based and episodic architectures are highly sensitive: extracting entities, constructing relations, and performing logical deduplication significantly increase format errors." — [Anatomy of Agentic Memory](https://arxiv.org/html/2602.19320v1)
- Benchmark saturation, "metric misalignment (e.g., F1 vs. semantic correctness), prompt sensitivity in LLM-as-a-judge evaluation, backbone dependence" are systemic. — [arXiv 2602.19320](https://arxiv.org/html/2602.19320v1); vendor LoCoMo claims are "Self-reported; not independently verified." — [Mem0 benchmark guide](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)
- Mem0 docs: mixing `infer=False` raw inserts with inferred memories "can save it twice." — [Mem0 docs](https://docs.mem0.ai/core-concepts/memory-operations)

### Inferences
- Deletion/retirement is the weakest operation across the field; systems that *version* and *timestamp* (Zep bi-temporal, Claude Code `modified`, git-backed MemFS) at least make staleness visible even if they do not solve it.
- Whole-document LLM rewrites are the single most dangerous maintenance operation for a text playbook: they cause context collapse/brevity bias and destroy provenance. Delta edits with ids are the documented remedy.
- Poisoning risk for a research agent is concrete: anything written into memory from fetched web content or tool output is an untrusted write; the lifecycle literature says the gate belongs at WRITE/STORE time with provenance, not at retrieval time.
- **[Ratchet]** A held-out gate on playbook edits is an instance of "Write Authorization" + "human/policy arbitration" in the VMG framework; git provides Rollbackability and partial Provenance Visibility for free; "Verified Forgetting" is not provided by any surveyed system and would need an explicit test (e.g., assert a deprecated rule no longer influences outputs).

### Gaps
- No quantitative study found of how often memory stores accumulate contradictions in *production* (only benchmark proxies).
- MemSecBench did not name the backends/harnesses in the abstract; I did not retrieve the body.
- No source quantifies "catastrophic overwrite" rates for note-level evolution schemes like A-MEM (the risk is inferred from mechanism, not measured).

## Key Question 4: How do file-based, plain-text memory approaches (CLAUDE.md, AGENTS.md, notes directories, playbooks) compare with vector/graph stores for coding and research agents?

### Takeaway
For coding and research agents, the 2025–26 evidence favors plain-text, file-based memory that the agent searches agentically (grep/read) over extracted-fact vector stores or knowledge graphs: a filesystem agent beat Mem0's graph variant on LoCoMo; MemGPT-style agentic search far outperformed Mem0/Cognee on test-time learning; ACE's text playbook matched a GPT-4.1 production agent; and Letta, Anthropic, and Claude Code have all converged on markdown files with an index. The main caveats are that (a) static repository-overview files (AGENTS.md/CLAUDE.md) show no measurable task-success benefit and add ~20% cost, so files should carry only non-derivable, specific instructions and learned corrections; and (b) text files need explicit size limits, indexes, delta-edit discipline, and dedup to avoid bloat and collapse.

### Cited Findings

**Adoption and anatomy of context files**
- AGENTS.md is "a README for agents: a dedicated, predictable place to provide the context and instructions" (build steps, tests, conventions). — [agents.md](https://agents.md/). Over 60,000 public GitHub repositories include a context file. — [Evaluating AGENTS.md](https://arxiv.org/html/2602.11988)
- Empirical study of 2,303 context files from 1,925 repos (Claude Code, Codex, Copilot): "these files are not static documentation but complex, difficult-to-read artifacts that evolve like configuration code through frequent, small additions." Content: test procedures 75.9%, implementation details 70.8%, architecture 68.1%; security 14.8%, performance 14.5%. The authors describe them as "a persistent long-term memory for the agent." — [Agent READMEs, arXiv 2511.12884](https://arxiv.org/abs/2511.12884); [ACM TOSEM](https://dl.acm.org/doi/10.1145/3840295)

**Do context files help? (negative result)**
- "providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average ... across different LLMs, coding agents, and for both LLM-generated and developer-committed context files." "instructions in the context files are well followed by coding agents, repository overviews ... are not helpful." Developer-committed files outperform LLM-generated ones "by a significant margin of 7% on average" but neither effect on success is statistically significant (p = 0.87 / 0.37). LLM-generated files reduced resolution by 0.5% (SWE-bench) and 2% (CTXbench); steps rose by 2.45–3.92 per task. Ablating "overview," "testing," or "tooling" sections did not significantly change accuracy. Recommendation: context files "should only contain specific additional instructions beyond what is already available in the codebase." — [Evaluating AGENTS.md, arXiv 2602.11988](https://arxiv.org/html/2602.11988)
- Claude Code's own guidance mirrors this: auto memory "skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes," and stores only `user`, `feedback`, `project`, and `reference` notes. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)

**Files vs. specialized memory tools on retrieval benchmarks**
- Letta: a plain filesystem agent (gpt-4o-mini, `grep`/`search_files`/`open` tools, tool rules forcing iterative search) scored 74.0% on LoCoMo vs Mem0g's reported 68.5%. "specialized memory tools that may have originally been designed for single-hop retrieval are less effective than simply allowing the agent to autonomously search through data with iterative querying." — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- MemoryAgentBench TTL (GPT-4o-mini backbone): MemGPT 89/83/79 vs Mem0 35/37/35 vs Cognee 34/42/42 on BANKING/CLINC/NLU; MIRIX (agentic multi-store) beat long-context GPT-4.1-mini on MH-Doc QA at lower cost. — [MemoryAgentBench](https://arxiv.org/html/2507.05257)
- Graph cost/benefit: Mem0g vs Mem0 lost single-hop (65.71 vs 67.13 J) and multi-hop (47.19 vs 51.15 J), won temporal (58.13 vs 55.51) and open-domain (75.71 vs 72.93), for +1.56 overall. — [Mem0 paper](https://arxiv.org/html/2504.19413). HippoRAG 2 reports structure-augmented RAG "drops considerably below standard RAG" on factual tasks unless passages are deeply integrated. — [arXiv 2502.14802](https://arxiv.org/abs/2502.14802)
- Graph/episodic architectures are "highly sensitive" to backbone quality via structured-output errors; append-only text systems are "relatively robust." — [Anatomy of Agentic Memory](https://arxiv.org/html/2602.19320v1)

**Industry convergence on markdown + index + git**
- Letta MemFS: "projects the agent's memory into Markdown files so the agent can read, edit, organize, and version what it learns"; `system/` files are in the prompt every turn, "Everything else stays out of context — the agent sees the file tree and reads what it needs"; "Edits become memory once they are committed and pushed." Rationale: "Files are simple, universal primitives that both humans and agents can work with using familiar tools ... agents can chain standard tools for complex queries over memory, use bash for batch operations ... or write scripts"; git "enables concurrent, collaborative work across multiple subagents, which can manage divergence and conflicts between learned context through standard git operations." — [Letta MemFS](https://docs.letta.com/letta-agent/concepts/memfs); [Agent SDK memory](https://docs.letta.com/agent-sdk/memory); [Context Repositories blog](https://www.letta.com/blog/context-repositories)
- Anthropic memory tool: file CRUD in a client-controlled directory; +39% with context editing on agentic search; for research agents "Memory stores key findings while context editing removes old search results, building knowledge bases that improve performance over time." — [Anthropic news](https://www.anthropic.com/news/context-management)
- Claude Code: MEMORY.md index with hard 200-line/25KB load limit, topic files, frontmatter `type` and `modified`, per-repo directory shared across worktrees, excluded from transcript cleanup; CLAUDE.md loads root-down, path-scoped `.claude/rules/` load on demand. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- ACE's playbook is text bullets with ids and helpful/harmful counters, merged deterministically and deduped by embeddings; contexts "contain detailed, domain-specific insights along with tools and code that are readily usable." — [ACE](https://arxiv.org/html/2510.04618v2)

**Governance advantages of text + VCS**
- The security survey lists "versioned snapshots, write logs, content-addressable records, and compression audits" as "the necessary architectural substrate for subsequent recovery," and names Rollbackability and Provenance Visibility as core primitives; W3C PROV is suggested for lineage. — [EMNLP 2026 survey](https://aclanthology.org/2026.emnlp-main.2296.pdf)
- Memp explicitly studies Build/Retrieval/Update strategies for a procedural repository and shows procedures "built from a stronger model" transfer to weaker models. — [Memp](https://arxiv.org/abs/2508.06433)

### Inferences
- For a *research* agent whose memory is mostly procedural (how to check a claim, which sources to trust, common pitfalls) plus a modest number of durable facts, the literature supports: raw episodes kept non-lossy on disk (Zep "episode subgraph" / Letta files / Claude Code transcripts), a small always-loaded playbook/index (Letta `system/`, MEMORY.md, ACE playbook), and on-demand topic files searched agentically. Vector/graph stores add value mainly for large, entity-rich, time-varying *fact* corpora with many users—not the typical profile of a single-harness research agent.
- The AGENTS.md null result plus Claude Code's "skip derivable info" rule imply a concrete content policy for a playbook: store corrections, confirmed approaches, and non-derivable project/domain facts; do not store descriptions of the codebase or generic workflow prose. Measure cost (steps/tokens) alongside accuracy, since instruction text reliably increases both.
- **[Ratchet]** Concrete, evidence-backed design patterns for a version-controlled text memory evaluated under a held-out gate:
  1. Itemized playbook entries with stable ids, provenance (which run/trajectory produced them), `modified` timestamps, and helpful/harmful counters updated from gated evaluations (ACE; Claude Code frontmatter).
  2. Delta edits (add/update/deprecate specific entries) rather than full rewrites; a deterministic merge plus embedding dedup pass (ACE grow-and-refine), and a periodic "defragmentation" into a bounded number of focused files (Letta: 15–25).
  3. A hard size budget on the always-loaded index (Claude Code: 200 lines/25KB; CLAUDE.md <200 lines) with overflow to topic files loaded on demand; treat growth in steps/tokens as a regression signal (AGENTS.md study).
  4. Separate human-authored instructions from agent-learned notes (CLAUDE.md vs auto memory; MemFS `system/`), and separate raw evidence from distilled strategy (Zep episodes vs entities; case- vs strategy-based experiential memory), so the gate can roll back strategy without losing evidence.
  5. Explicit deprecation rather than deletion (Memp; Zep `t_invalid`), plus a regression test that deprecated guidance no longer changes behavior (Verified Forgetting is unsupported everywhere else).
  6. Learn from failures as well as successes (ReasoningBank) and from execution feedback without labels where labels are scarce (ACE +14.8% label-free), but keep ground-truth-gated evaluation because label-free adaptation underperforms gated adaptation in ACE's own results.
  7. Evaluate memory with a Context Saturation Gap: compare the harness with the playbook against a full-context/no-memory baseline on the held-out set; a playbook that does not beat "just put the evidence in context" is not earning its tokens (Anatomy survey; Zep/Mem0 full-context baselines).
  8. Treat any write sourced from fetched web content as untrusted: gate at write time with provenance tags and keep git history for rollback (LTM security survey; MemSecBench persistence 84.2%).

### Gaps
- No controlled study compares a versioned text playbook against a vector or graph store on a *scientific claim-checking* or deep-research task; the closest evidence is LoCoMo (Letta files), MemoryAgentBench TTL (MemGPT vs Mem0), AppWorld/FiNER (ACE), and SWE-bench/CTXbench (AGENTS.md), none of which is a research-agent benchmark.
- The AGENTS.md study evaluates static, mostly human/LLM-written overview files; it does not test *learned* correction notes (Claude Code auto memory / ACE-style playbooks) on coding tasks, so it does not directly bound the value of a self-improved playbook.
- I found no published numbers for Claude Code auto memory's effect on task success, nor for Letta MemFS/Context Repositories beyond the filesystem LoCoMo result.
- Dynamic Cheatsheet's own results were not retrieved (only ACE's comparisons against it).
